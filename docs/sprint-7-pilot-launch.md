# Launching the controlled Relay pilot

These steps prepare and run a limited test. They are not production deployment instructions. Do not expose the service publicly, enter production secrets into evidence files, or start until the checklist has named owners and all preflight items pass.

1. **Approve scope.** Name the pilot owner, operators, approved Android devices, permitted data sources, date window, maximum sample count, retention period, incident contact, and whether SMS is included. Confirm participants may use the chosen receipt/SMS data.
2. **Create the observation record.** Copy `sprint-7-pilot-checklist.md` into a dated run record. Add environment, Relay package hash, backend revision/package hash, Android APK hash, device IDs, operator IDs, and evidence locations. Do not record passwords, bearer tokens, database credentials, object-store secrets, or unnecessary receipt contents.
3. **Prepare private infrastructure.** Provision the already-defined Relay PostgreSQL, private object storage, API, and worker in an access-controlled pilot environment. Configure backups, retention, log access, rate limits, TLS, network restrictions, and monitoring appropriate to the environment. Sprint 7 did not perform this deployment.
4. **Verify the backend.** Run migrations through `0006`, confirm `alembic current`, run `alembic check`, verify health/readiness, confirm the worker is consuming the intended queue, and perform a protected object read. Create the operator account through the approved administrative process.
5. **Verify the package.** Compare the extracted `relay-sprint-7.zip` SHA-256 with `relay-sprint-7.sha256`. Build/deploy from that reviewed source only. Record resulting artifact hashes. Do not use the unsigned release APK as a distributable production binary.
6. **Prepare Android.** Produce or select the approved pilot-signed APK, inspect its permissions, verify its hash, install it on each approved device, complete Relay enrollment, and confirm the device is ACTIVE. Verify consent before enabling SMS. Select the approved SAF source before image collection and synchronize configuration.
7. **Prepare the operator UI.** In a supported browser, confirm login, refresh/re-authentication behavior, English, Arabic, RTL, themes, protected images, review, duplicate comparison, processing, export, and contextual Help. Explain that locale/theme persist but the administrator token deliberately does not.
8. **Prepare samples.** Assign opaque sample IDs and independently record expected class, amount/currency, reference/serial, date/time, sender, and recipient before Relay processes them. Include a normal receipt, a distinct second transaction, two different images with the same reference, and a review candidate where safe. Add SMS only when explicitly approved.
9. **Run test cases in order.** Execute P01–P08 first with the smallest sample set. If safe, continue through language, bidi, responsive, keyboard, session, failure, optional SMS, and reconnect cases. Record collection, upload, and processing timestamps from evidence rather than estimates.
10. **Reconcile.** Freeze the pilot sample set. Compare source expectations, transaction data, reviewed values, deterministic duplicate groups, dashboard figures, and Excel output. Preserve both successful and failed evidence.
11. **Stop on safety triggers.** Stop collection immediately for unauthorized data, public exposure, credential leakage, lost provenance, evidence deletion, uncontrolled duplication, corrupted audit history, or a BLOCKER. Preserve logs and identifiers, revoke affected access, and follow the named incident process.
12. **Close the run.** Mark each of the sixteen criteria pass/fail/not applicable with its denominator and evidence. Classify findings, obtain the pilot owner's sign-off, apply the post-pilot decision framework, and choose the next work explicitly. Do not start another sprint automatically.

The pilot may demonstrate operational usefulness of collection, extraction, duplicate grouping, review, and reporting. It cannot prove that a financial transaction occurred and must not be described as authenticity or fraud validation.
